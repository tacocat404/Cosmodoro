# 우주뽀모도로를 영화처럼 찍고 포스터처럼 인쇄하라

우주뽀모도로를 "100배 더 멋있게" 만드는 길은 효과를 더 얹는 데 있지 않다. 지금 있는 장면이 **'촬영된 것처럼' 보이게 만들고, 순항 중 움직임은 오히려 덜어내는 데** 있다. 출발점은 두 페이지를 **"1960년대 NASA 미션 필름을 국립공원 포스터로 인쇄한 것"**이라는 한 문장으로 묶는 일이다. 메인 페이지는 인쇄물, 비행 페이지는 필름, 도착은 필름의 한 프레임이 포스터로 인쇄되는 순간이 된다. 기술적으로는 두 가지를 먼저 한다. 매 프레임 픽셀마다 fbm을 여러 번 돌리는 행성 셰이더를 텍스처로 **굽고(bake)**, 두 페이지 모두 상한 없이 돌고 있는 렌더 루프에 집중 중 30fps 상한과 탭 숨김 정지를 건다. 그렇게 되찾은 GPU 예산은 단일 태양의 날카로운 명암 경계, 대기 산란, AgX/LUT 컬러 그레이딩, 반짝이지 않는 별, 절제된 렌즈 효과에 다시 쓴다. 연출은 3~4초짜리 상태 전환(탑승 → 발사 → 도착 포스터)에 몰아 쓰고, 25~90분의 순항은 거의 멈춘 '선실 창문'으로 둔다. 이 방향이 맞는 이유는 두 가지다. Orbital Focus와 FocusFlight가 이미 3D 비행 타이머를 내놓아 3D 자체는 차별점이 되지 못하고 ([Product Hunt](https://www.producthunt.com/products/orbital-focus); [AppFollow](https://apps.appfollow.io/ios/focusflight-deepfocus-timer/6648771147?country=it)), 주변시의 움직임은 색이나 모양보다 주의를 세게 끈다 ([Bartram et al.](https://www.interruptions.net/literature/Bartram-Interact01.pdf)). 실행 순서는 0단계 성능·측정 기반 → 1단계 빛·별·HUD 퀵윈 → 2단계 렌더링 트랙과 3단계 의식·사운드 트랙 병행 → 4단계 패스포트·여정 지도·통계다. 사용자가 먼저 정할 것은 두 가지다. three.js를 r160에 둘지 r167로 올릴지(r167이면 pmndrs postprocessing 6.36.0 호환 범위 안에서 Khronos Neutral과 수정된 AgX를 함께 얻는다), 그리고 단일 HTML 원칙을 외부 에셋에 얼마나 열지다.

## 3D 비행 타이머는 이미 흔하다: 차별점은 한 문장짜리 아트 디렉션이다

우주·비행 메타포는 집중 앱 시장에서 이미 붐비는 자리다. FocusFlight는 세션마다 출발지와 도착지가 있는 항로를 그린다. FlightLog에는 출발·도착 도시, 집중 시간, 비행 거리가 쌓이고, 3D·위성 지도 모드와 기내 앰비언스도 있다 ([AppFollow](https://apps.appfollow.io/ios/focusflight-deepfocus-timer/6648771147?country=it)). Orbital Focus는 점화·Max-Q·단 분리 순간에 햅틱이 울리는 발사 카운트다운을 갖췄고, 긴 세션을 'burn'과 'coast'로 나눈다. 한 사용자는 화성 도착 애니메이션을 콕 집어 칭찬했다 ([Product Hunt](https://www.producthunt.com/products/orbital-focus)). 별가루로 행성을 모으는 Let's Focus, 프로젝트마다 행성을 빚는 Exocus, 실제 HYG 항성 목록 사이를 여행하는 Star Focus도 있다 ([Let's Focus](https://apps.apple.com/app/id1525639438); [Exocus](https://apps.apple.com/us/app/-/id6448949389); [Star Focus](https://apps.apple.com/app/id6766443541)). 이름이 비슷한 비행 앱이 여럿이라 서로 구분하기도 어렵다 ([mergeek](https://mergeek.com/en/latest/K5lYgAMDpMJn1wx2)). 그러니 **"3D 우주선이 날아간다"는 사실만으로는 더 이상 멋이 생기지 않는다.** 남는 차별점은 세 가지다. 시각 언어의 일관성, 세션을 감싸는 의식, 그리고 쌓이는 기록의 깊이다.

일관성을 만드는 가장 싼 도구는 작업할 때마다 꺼내 볼 수 있는 한 문장이다. Bethesda는 Starfield의 미술에 'NASA-Punk'라는 이름을 붙였고, 리드 애니메이터는 이 말 덕분에 아트 팀이 일관성을 지켰다고 했다. 같은 원칙에서 홀로그램과 터치스크린 대신 손에 잡히는 물리 스위치를 골랐다 ([VGC](https://www.videogameschronicle.com/news/starfield-developers-discuss-the-games-nasa-punk-aesthetic)). No Man's Sky는 "살아 움직이는 SF 소설 표지"를 목표로 삼았다 ([No Man's Sky](https://www.nomanssky.com/2016/04/art-of-no-mans-sky/)). Outer Wilds는 회화풍을 버리고 국립공원 포스터의 그래픽 단순성, 날카로운 형태, 큰 스케일의 그라디언트로 옮겨 갔다 ([Mobius Digital](https://www.mobiusdigitalgames.com/news/our-new-style)). JPL의 "Visions of the Future" 포스터는 WPA 국립공원 포스터 양식을 과학자의 검수를 거친 내용에 입혔다. 금성 포스터의 구불구불한 글자는 구름을 떠올리게 하려고 일부러 그렇게 그렸다 ([I'm Just Creative](https://imjustcreative.com/nasa-visions-of-the-future-poster-series/2019/02/20); [Graphic Artists Guild](https://graphicartistsguild.org/space-exploration-posters-courtesy-of-the-jet-propulsion-lab/)). 네 사례가 가리키는 공식은 같다. **검증된 과학 콘텐츠 위에 향수 어린 그래픽 시스템을 하나 빌려 와서 끝까지 지킨다.**

우주뽀모도로에 맞는 문장은 **"1960년대 NASA 미션 필름을 국립공원 포스터로 인쇄한 것"**이다. 이 문장은 두 페이지를 갈라놓지 않고 역할을 나눈다. 메인 페이지는 *인쇄물*이다. 휘도를 3~5단으로 나눈 포스터화 행성, 멈춰 있는 필름 그레인, 아주 약한 인쇄 어긋남(misregistration), 스위스 그리드 위의 평평한 타이포가 여기에 속한다. 비행 페이지는 *필름*이다. 함선에 고정된 카메라, 하나의 태양, 실제 렌즈에서 생기는 아티팩트가 여기에 속한다. 도착은 필름의 한 프레임이 포스터로 인쇄되는 순간이다. 과목 행성마다 그 세계를 떠올리게 하는 타이틀 레터링을 준다. 화성은 녹슨 스텐실, 금성은 흐르는 필기체, 토성은 자간을 넓게 벌린 기하학 대문자, 해왕성은 차갑고 가는 세리프다. 본문 UI는 중립적인 그로테스크 하나로 통일한다. 그러면 JPL 포스터의 문법을 그대로 옮겨 올 수 있다.

색 정책도 이 문장에서 나온다. The Martian의 촬영감독 Dariusz Wolski는 붉은 외부와 대비되도록 거주 모듈 실내를 일부러 차갑게 만들어 "붉은색으F로부터의 해방"을 연출했다 ([Below the Line](https://www.btlnews.com/awards/contender-cinematographer-dariusz-wolski-the-martian/)). Ad Astra는 적외선 개조 카메라로 하늘을 순수한 검정으로, 하이라이트를 하얗게 날린 뒤 필름 컬러를 얹었다 ([befores & afters](https://beforesandafters.com/2019/09/30/shooting-in-the-desert-using-infra-red-and-making-a-moon-rover-melee/)). Dune: Part Two도 하코넨 장면을 적외선으로 찍었다 ([No Film School](https://nofilmschool.com/dune-part-2-infrared)). 이를 우주뽀모도로에 옮기면 이렇다. **비행 페이지 전체를 모노크롬에 가까운 그레이드로 누르고, 색은 목적지 행성과 신호색 하나에만 남긴다.** 그러면 흑백 메인 페이지와 컬러 비행 페이지 사이의 단절이 사라지고, 목적지 행성은 화면에서 유일하게 색을 가진 '목표'가 된다. 반대로 유리(글래스모피즘) 쪽으로 방향을 트는 것은 피해야 한다. iOS 26의 Liquid Glass는 반투명 레이어가 글자를 읽기 어렵게 만든다는 반발을 불렀고, Apple은 iOS 26.1 베타에서 유리를 평평하게 누그러뜨리는 'Tinted' 옵션을 시험했다 ([BGR](https://bgr.com/tech/ios-26-beta-3-liquid-glass-complaints/); [Gulf News](https://gulfnews.com/technology/companies/apple-yields-tinted-control-in-ios-261-beta-4-tones-down-liquid-glass-after-backlash-1.500315176)). 움직이는 3D 장면 위의 반투명 패널은 이 문제를 더 키운다. 지금의 다크 에디토리얼·포스터 방향은 버릴 대상이 아니라 다듬을 대상이다.

## 보이지 않는 곳에서 새는 GPU를 먼저 막는다: 굽고, 묶고, 쉬게 하라

코드를 열어 보면 출발선이 분명하다. `v4-flight.html`은 `requestAnimationFrame`을 상한 없이 돌리고, DPR은 1.5로 묶여 있다. `UnrealBloomPass`는 화면 전체 해상도로 만들어지고(강도 0.6, 임계 1.15), ACES Filmic(노출 1.05)과 `OutputPass`를 쓴다. 행성 셰이더는 최대 7옥타브 루프의 fbm을 한 픽셀에서 여러 번 부른다. 거리에 따라 옥타브를 줄이는 LOD가 일부 들어가 있긴 하다. `v3-main.html`의 영웅 행성도 실시간 fbm을 DPR 2로 상한 없이 그린다. 두 파일 모두 `visibilitychange` 처리가 없다. 다행히 은하수 하늘은 이미 1024 HalfFloat 큐브 렌더 타깃에 구워져 있다. 이 장면의 GPU 프래그먼트 비용은 대략 **fps × 화면 픽셀 수(DPR²에 비례) × 픽셀당 셰이더 비용**으로 늘어난다. 60fps·DPR 2에서 30fps·DPR 1.25로 내리면 0.5 × (1.25²/2²) ≈ 0.2이니, 프래그먼트 작업이 약 80% 줄어든다. 측정값이 아니라 1차 산술이지만, 노트북 팬이 도느냐 마느냐를 가를 만큼 큰 차이다.

Three.js에는 fps 상한 기능이 없어서 `setAnimationLoop` 안에서 직접 프레임을 건너뛰어야 한다 ([Needle forum](https://forum.needle.tools/t/fps-limit/1176)). 이때 모든 움직임은 프레임 수가 아니라 시간 차(delta)로 계산해야 한다. Chrome의 에너지 절약 모드는 디스플레이 주사율을 낮추는데, 프레임당 16.67ms를 가정한 루프는 이 모드에서 "두 배 느리게" 돈다 ([Chrome for Developers](https://developer.chrome.com/blog/memory-and-energy-saver-mode)). 백그라운드 탭에서는 Chrome이 rAF를 아예 부르지 않는다 ([Chrome blog](https://developer.chrome.com/blog/background_tabs)). 그러니 탭으로 돌아올 때 delta를 0.1초 정도로 잘라야 장면이 순간이동하지 않는다.

가장 크게 새는 곳은 행성이다. 9개 행성이 매 프레임, 매 픽셀 fbm을 계산하지만 행성 표면은 실제로 변하지 않는다. 텍셀마다 셰이더를 돌려 렌더 타깃에 **초기화 때 한 번만** 그리는 방법은 이미 튜토리얼로 정리돼 있다 ([Bekk](https://blogg.bekk.no/procedural-planet-in-webgl-and-three-js-part-2-33d99bbb2256)). ShaderMaterial을 텍스처로 굽는 커뮤니티 라이브러리도 있다. 다만 관찰자 위치에 따라 달라지는 효과는 구울 수 없다는 단서가 붙는다 ([three.js forum](https://discourse.threejs.org/t/threejs-shader-baker/71225)). 그래서 경계를 이렇게 긋는다. 알베도와 높이는 굽고, 조명·명암 경계·대기·구름 흐름은 실시간으로 남긴다. 가스 행성에는 더 극적인 사례가 있다. 한 상용 Unity 행성 셰이더는 가스 행성 셰이더를 저차 도메인 워핑과 위도 방향 사인 띠로 바꾼 뒤 1080p에서 **성능이 두 배 넘게 올라 140fps를 넘겼다** ([Unity Discussions](https://discussions.unity.com/t/released-procedural-planet-generation-shaders-in-editor-baking-custom-space-lighting/1700475)). 메모리 예산은 산술로 정한다. 2048×1024 RGBA8에 밉맵을 붙이면 약 11MB라 9개면 100MB에 가깝다. 그러니 히어로 행성만 2048로 두고, 나머지는 1024×512(약 2.8MB)나 512 큐브면으로 낮춘다. 참고로 4096² 텍스처 하나는 밉맵을 포함해 약 85MiB를 차지한다 ([Utsubo](https://www.utsubo.com/blog/threejs-best-practices-100-tips)). 큐브맵에 구우면 극점이 몰리는 현상과 UV 이음매가 사라진다. 발사 카운트다운 동안 한 프레임에 한 행성씩 나눠 구우면 끊김도 숨길 수 있다. 굽는 루틴은 몇 번이고 다시 실행할 수 있어야 한다. 긴 세션 중에 WebGL 컨텍스트가 날아가면 렌더 타깃 내용도 함께 사라지기 때문이다.

후처리와 별도 손볼 곳이다. `UnrealBloomPass`는 내부적으로 절반 해상도 브라이트 패스에서 시작해 5단 밉 체인을 블러한다 ([three.js docs](https://threejs.org/docs/pages/UnrealBloomPass.html)). 그래도 비용은 픽셀을 채우는 속도에 묶인다. 한 사용자는 공식 블룸 예제가 Intel i7 MacBook Pro 2020의 Safari 전체 폭에서 20fps를 겨우 넘다가, 창 폭을 약 400px로 줄이자 60fps가 됐다고 보고했다. M1 MacBook Air에서는 처음부터 60fps였다 ([three.js forum](https://discourse.threejs.org/t/unrealbloompass-poor-performance-on-macos-safari-with-intel/42606)). 이런 장면에서 후처리를 절반 해상도로 돌리면 프레임레이트가 대략 두 배가 된다 ([Utsubo](https://www.utsubo.com/blog/threejs-best-practices-100-tips)). 그러니 블룸 해상도는 0.5배로 넘기고, 저사양 티어에서는 블룸을 끄고 태양·엔진 뒤의 가산 스프라이트로 대신한다. 수천~수만 개의 포인트 스프라이트는 드로콜 하나라 싸 보이지만, 실제 비용은 겹쳐 그리기(overdraw)에서 나온다. 배경 별 대부분은 이미 있는 하늘 큐브에 함께 굽고, 시차가 보이는 근거리 별 2~5천 개만 Points로 남긴다.

마지막은 적응형 품질이다. DPR은 `Math.min(devicePixelRatio, 2)` 이하로 묶는다. 3배율 화면의 폰은 1배율보다 픽셀이 9배 많다 ([Utsubo](https://www.utsubo.com/blog/threejs-best-practices-100-tips)). drei의 `PerformanceMonitor`는 250ms 단위 평균 fps를 여러 번 모아 일정 비율을 넘을 때만 품질을 올리거나 내리고, 몇 번 오락가락하면 안전한 기준선에 고정한다 ([drei docs](https://drei.docs.pmnd.rs/performances/performance-monitor)). 이 히스테리시스 로직을 바닐라 JS로 옮기되 조건 하나를 바꿔야 한다. 30fps 상한 아래에서는 "상한을 넘으면 품질을 올린다"는 조건이 영영 발동하지 않으므로, "상한의 0.85배 아래로 떨어지면 품질을 내린다"를 기준으로 삼는다. `@pmndrs/detect-gpu`는 초기 티어(0~3)를 잡는 데 쓸 만하다. 하지만 데이터 원천인 gfxbench가 **2025년 12월부터 업데이트를 멈춰** 최신 GPU는 빠져 있을 수 있다 ([GitHub detect-gpu](https://github.com/pmndrs/detect-gpu)). 배터리 API는 Baseline이 아니고 HTTPS에서만 동작하니 보조 힌트로만 쓴다 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/getBattery)).

WebGPU 전환은 지금의 답이 아니다. WebGPU는 이제 주요 브라우저 모두에서 돌아간다 ([web.dev](https://web.dev/blog/webgpu-supported-major-browsers)). 그러나 r183 포럼 벤치마크에서 WebGPURenderer는 CPU 렌더 시간이 4.5ms 대 9.7ms, 첫 프레임이 32ms 대 167ms로 오히려 느렸다 ([three.js forum](https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904)). 게다가 GLSL 셰이더는 TSL로 전부 다시 써야 한다 ([ICS MEDIA](https://ics.media/en/entry/250501/)). 그 벤치마크는 메시가 많은 CAD 장면이라 이 앱과 같은 조건은 아니다. 다만 우주뽀모도로의 병목은 드로콜이 아니라 픽셀이고, WebGPU의 강점은 그 병목을 겨냥하지 않는다.

| 티어 | DPR | fps 상한 | 블룸 | 행성 | 별 |
|---|---|---|---|---|---|
| 3 (고성능) | min(dpr, 2) | 전환·조작 60 / 집중 30 | 0.5배 해상도 | 베이크 + 히어로만 실시간 1~2옥타브 | 근거리 Points 5천 + 하늘 큐브 |
| 2 (기본) | min(dpr, 1.5) | 30 | 0.5배 | 베이크만 | 3천 + 하늘 큐브 |
| 1 (저사양) | 1 | 24~30 | 끔(가짜 글로우 스프라이트) | 512~1024 베이크 | 2천 + 하늘 큐브 |
| 0 / 정적 | — | 정지 | — | 사전 렌더 이미지 + 느린 CSS 드리프트 | — |

이 표는 연구 노트의 권장치를 이 앱 구조에 맞춘 출발점이다. 성공 여부는 두 가지로 판정한다. Windows 작업 관리자의 GPU %와 전력 사용 열이 실제로 내려가는지, 그리고 `renderer.info.memory`가 90분 동안 평평하게 유지되는지다. fps 상한이 배터리나 발열을 몇 분, 몇 와트 줄이는지에 대한 공개 측정치는 찾지 못했다. 그러니 직접 A/B로 재야 한다.

## '촬영된 우주'는 다섯 가지 광학 신호로 만들어진다

Interstellar 제작진의 논문은 사실감과 물리적 정확성이 다르다는 점을 분명히 보여 준다. 완전히 사실적인 강착 원반은 한쪽으로 지나치게 치우쳐 블랙홀 그림자가 거의 보이지 않았다. 제작진은 이를 받아들일 수 없다고 보고 도플러 효과를 뺐고, 회전도 a/M=0.6으로 늦췄다. 반대로 CG에는 놀런의 IMAX 렌즈에서 측정한 베일링 플레어를 일부러 더해 실사 카메라 화면과 이어지게 했고, 깜빡임을 없애는 필터링에 공을 들였다 ([James et al. 2015](https://ar5iv.arxiv.org/html/1502.03808)). 즉 사실감은 **카메라의 행동과 읽기 쉬움**에서 나온다. 거리를 압축하고 목적지 행성을 처음부터 작은 원반으로 보여 주는 것은 반칙이 아니라 Interstellar가 쓴 바로 그 면허다. 그 위에 다음 다섯 가지 신호를 쌓는다.

### 신호 1: 태양은 하나, 밤면은 검게

Wolski는 The Martian의 그린스크린 무대에서도 그림자 일관성을 위해 단일 광원을 고집했다 ([fxguide](https://www.fxguide.com/?p=60903)). Interstellar는 키·필·실내 조명을 따로 나누지 않고 한 번에 촬영해, 실제 촬영에서 생기는 아티팩트까지 화면에 담았다 ([fxguide](https://www.fxguide.com/?p=55891)). 지금 비행 페이지에는 `HemisphereLight`(0.12)와 차가운 보조 `DirectionalLight`(0.5)가 깔려 있다. 이 둘을 빼거나 크게 줄이고, 모든 행성·함선·메인 페이지 행성을 같은 태양 벡터로 비춘다. 그러면 밤면이 거의 검게 떨어지면서 NASA 사진 특유의 초승달 실루엣이 생긴다. 함선에는 반대편에서 오는 차가운 림 라이트와, 행성 평균 색을 띤 아주 약한 '행성광'만 더한다. 코드 몇 줄로 끝나지만 체감 변화는 가장 큰 항목이다.

### 신호 2: fresnel 테두리 대신 진짜 대기

현재 대기는 `BackSide`·가산 블렌딩 셸, 즉 fresnel 테두리다. 다음 단계는 같은 구 메시에서 시선 광선을 대기 구·행성 구와 교차시키고, 그 사이를 8~12개 샘플로 레이마칭하는 산란 셸이다. Maxime Heckel은 2026년 글에서 이 방식을 WebGL로 구현하면서 지구형 계수를 공개했다. Rayleigh 스케일 높이 8km, β=(0.0058, 0.0135, 0.0331), Mie 스케일 높이 1.2km, 오존 흡수 항이고, 화성 프리셋도 함께 실었다. Hillaire 2020 방식의 투과율 LUT로 바꾸자 '무시할 수 없는' 속도 향상이 있었지만, sky-view LUT에서는 띠와 깜빡임이 생겼다고 한다 ([Maxime Heckel](https://blog.maximeheckel.com/posts/on-rendering-the-sky-sunsets-and-planets/)). 가장 싼 길은 GPU Gems 2의 O'Neil 방식이다. 광학 깊이 표를 닫힌 식으로 대체하고 일의 대부분을 정점 셰이더로 옮긴다. 다만 대기 두께가 행성 반지름의 2.5%라는 고정 비율에 맞춰져 있다 ([NVIDIA GPU Gems 2](https://developer.nvidia.com/gpugems/gpugems2/part-ii-shading-lighting-and-shadows/chapter-16-accurate-atmospheric-scattering)). 기성 라이브러리 `@takram/three-atmosphere`는 three ≥ 0.170을 요구하고 사실상 지구 대기 전용이라 r160에 바로 넣을 수 없다 ([jsDelivr package.json](https://cdn.jsdelivr.net/npm/@takram/three-atmosphere/package.json); [GitHub](https://github.com/takram-design-engineering/three-geospatial/tree/main/packages/atmosphere)). 그래서 레이마칭 셸을 직접 쓰고, 티어 1에서는 샘플을 6×3으로 줄이거나 O'Neil로 바꾸는 것을 권한다. 이 셸이 만드는 파란 가장자리, 주황빛 명암 경계, 역광에서 번지는 전방 산란 후광이 fresnel 대비 가장 큰 사실감 도약이다. 셸은 행성이 덮는 픽셀만 계산하므로 비용이 화면 전체로 번지지 않는다.

표면은 층으로 쌓는다. 구운 높이 텍스처의 유한 차분으로 노멀을 만들면 명암 경계에 요철이 산다. 구름은 표면보다 조금 빨리 도는 셸로 따로 두고, 표면 셰이더에서 태양 방향으로 어긋난 위치의 구름을 한 번 더 읽어 그림자를 드리운다. 토성 고리는 Henyey-Greenstein 위상 함수(g≈0.7)로 역광일 때 밝아지게 하고, 행성 셰이더에서 고리 평면을 빛 방향으로 투영해 고리 그림자를 얹는다. 연구 노트는 두 효과 모두 텍스처 읽기 한 번 정도의 비용으로 추정했다(측정값은 아니다). 실제 행성 지도를 쓰고 싶다면 Solar System Scope 텍스처가 CC BY 4.0이라 상업적 사용까지 가능하다. 다만 천왕성·해왕성은 2k 해상도만 있다 ([Solar System Scope](https://www.solarsystemscope.com/textures/)).

### 신호 3: 우주의 별은 반짝이지 않는다

별의 반짝임은 대기 때문에 생기는 현상이라 우주 시점에서는 없어야 하고, 점으로 보이는 별에서 가장 중요한 것은 색이다 ([Khronos forum](https://community.khronos.org/t/what-is-the-best-most-realistic-method-of-rendering-a-starfield/14296)). 색은 흑체 온도(2,500~30,000K) LUT로 주되 주황색 K·M형 쪽으로 기울인다. 밝기는 '어두운 별은 아주 많고 밝은 별은 극소수'인 멱법칙 분포를 따른다. 1px보다 작은 별은 크기 대신 알파로 줄여야 지글거림이 생기지 않는다. 블룸 임계는 가장 밝은 0.5% 정도의 별만 넘게 하고, JWST식 회절 스파이크는 5~20개의 '영웅 별'에만 붙인다. 은하수 큐브에는 도메인 워핑으로 만든 어두운 먼지띠와, 따뜻한 중심부에서 푸른 팔로 넘어가는 색 변화를 덧칠한다. 성운이 필요하면 매 프레임 레이마칭하지 말고 시작할 때 하늘 큐브에 한 번 굽는다. Gaia Sky의 전체 화면 레이마칭 구조가 좋은 참고가 된다. 다만 그 성운이 빌려 온 Shadertoy 코드는 기본 라이선스가 CC BY-NC-SA 3.0이라 그대로 복사하면 안 된다 ([Gaia Sky blog](https://tonisagrista.com/blog/2024/rendering-aurorae-nebulae/)).

### 신호 4: 톤매핑과 그레이딩이 '필름 스톡'을 정한다

r160에는 ACES Filmic과 '갓 들어온' AgX가 있다. AgX의 색역 매핑 수정은 r161에서야 들어왔다 ([three.js forum](https://discourse.threejs.org/t/is-agx-tonemapping-implemented-correctly/60609); [PR #27413](https://github.com/mrdoob/three.js/pull/27413)). UI 색을 충실히 지키는 Khronos PBR Neutral은 r162에 추가됐다 ([three.js r162](https://github.com/mrdoob/three.js/releases/tag/r162)). 한편 pmndrs `postprocessing@6.36.0`의 peer 범위는 three ≥ 0.157, < 0.168이다 ([jsDelivr](https://cdn.jsdelivr.net/npm/postprocessing@6.36.0/package.json)). 이 두 사실을 겹치면 **수정된 AgX, Neutral, pmndrs 6.36.0을 함께 쓸 수 있는 가장 새 버전이 r167**이라는 결론이 나온다. 단, 6.36.0 안에 AGX·NEUTRAL 모드가 실제로 들어 있는지는 직접 확인해야 한다. pmndrs는 여러 효과를 하나의 `EffectPass`로 합치고, HDR 작업에는 `HalfFloatType` 프레임버퍼를 권한다 ([GitHub pmndrs/postprocessing](https://github.com/pmndrs/postprocessing)). 이 체인 위에서 밉맵 블룸(휘도 임계 ≥ 1.0) → 톤매핑 → 33³ `.cube` LUT 그레이드 → 비네트 → 그레인을 한두 패스로 묶는다. LUT 하나로 청록 그림자, 따뜻한 하이라이트, 살짝 들뜬 검정 같은 필름 룩을 만들 수 있고, 비용은 픽셀당 3D 텍스처 읽기 한 번이다. three 자체의 `LUTPass`로도 같은 일을 할 수 있다 ([three.js docs](https://threejs.org/docs/pages/LUTPass.html)). import map에서는 jsDelivr의 `+esm` 대신 패키지 자체 ESM 빌드를 연결해야 three가 두 벌 로드되는 사고를 피한다.

### 신호 5: 렌즈는 진짜처럼, 그러나 아주 약하게

ektogamat의 바닐라 렌즈 플레어는 후처리 파이프라인 없이 씬 객체로 붙고, 라이선스는 CC0다. 문서는 `starBurst`가 일부 GPU에서 매우 무겁다고 경고한다 ([GitHub ektogamat](https://github.com/ektogamat/lensflare-threejs-vanilla)). 그러니 `starBurst`는 끄고, 플레어는 태양에만 쓰고, 고스트는 작게 줄이고, 약한 수평 아나모픽 줄만 남긴다. 색수차는 가장자리에만 0.0005~0.0015로, 비네트는 0.3~0.5로 둔다. 그레인은 WebGL 패스 안에서 처리하고, 정지시키거나 12~24fps로만 갱신한다. HUD 글자 위에는 CSS 그레인을 덮지 않는다.

함선이 '프리미티브'처럼 보이는 이유는 반사할 환경이 없어서다. 검은 구, 태양 방향의 큰 따뜻한 발광 면, 희미한 푸른 림 패널, 실제 하늘 큐브로 맞춤 환경 씬을 만들어 PMREM으로 한 번 구우면, 금속 표면이 장면의 빛과 맞아떨어지는 반사를 얻는다. 기성 반사 환경이 필요하면 Poly Haven HDRI를 쓸 수 있다. 모든 자산이 CC0다 ([Poly Haven](https://polyhaven.com/license)). 실제 우주선 모델이 필요하면 NASA 3D Resources가 '저작권 없음'으로 공개돼 있다 ([NASA 3D Resources](https://github.com/nasa/NASA-3D-Resources)). 절차적 함선을 유지한다면 할 일은 이렇다. 캔버스 알베도 옆에 거칠기·금속성·노멀 캔버스를 함께 만들어 패널 이음새를 홈으로 새긴다. 모서리는 베벨 처리한다. 모서리에 맺히는 하이라이트가 '모델처럼' 보이게 하는 핵심 단서라는 것이 연구 노트의 판단이다. 그리블은 `InstancedMesh`로 수백 개를 드로콜 하나에 얹는다. 항법등은 좌현 빨강, 우현 초록으로 2~3초 주기의 느린 점멸을 주고, 엔진 노즐은 HDR 발광(강도 5~20)으로 만들어 블룸이 잡게 한다.

## 드라마는 4초의 전환에, 나머지 89분은 '선실 창문'에

주의 연구는 이 판단을 뒷받침한다. 움직임은 색이나 모양보다 강한 주의 단서이고, 주변시에서는 더욱 그렇다 ([Bartram et al.](https://www.interruptions.net/literature/Bartram-Interact01.pdf)). 시선 추적 연구에서 광고가 많이 움직일수록 본문 텍스트에 대한 고정과 되돌아 읽기가 늘었다 ([Lan, Liao & Kruger](https://citedrive.com/en/discovery/do-advertisements-disrupt-reading-evidence-from-eye-movements)). 화면 속 자연 이미지가 주의를 회복시킨다는 주의회복이론(ART)의 효과는 실제 자연보다 약했고, 지속 주의와 경계 과제는 개선 항목에 들지 못했다 ([NAAEE](https://eepro.naaee.org/research/eeresearch/attention-restoration-theory-ii-systematic-review-clarify-attention-processes)). 우주 장면이 공부를 돕는다고 주장할 근거는 없다는 뜻이다. WCAG 2.3.3은 필수가 아닌 움직임을 끌 수 있어야 한다고 요구하며, 패럴랙스를 대표 사례로 든다 ([W3C](https://w3c.github.io/wcag/understanding/animation-from-interactions.html)). 다만 3D 우주 배경이 학습에 미치는 영향을 직접 검증한 연구는 찾지 못했다. 아래 원칙은 이 근거들에서 끌어낸 설계 판단이다.

순항의 기준은 Interstellar다. 놀런은 카메라를 우주선 모형에 고정하라고 요구했고, 폭발 장면에서는 카메라를 펠리컨 케이스에 넣어 모형에 직접 물렸다 ([fxguide](https://www.fxguide.com/?p=55891)). 우주뽀모도로도 추적 카메라를 함선에 단단히 고정하고 수 초 단위의 관성 지연만 남긴다. 집중 중에는 컷도, 궤도 회전도 없다. Elite Dangerous의 초항행(supercruise) 논쟁에서 일부 플레이어는 긴 이동을 설계 결함이라 부르지만, 다른 이들은 그 덕분에 우주의 크기를 느낀다고 말한다 ([Frontier forums](https://forums.frontier.co.uk/goto/post?id=9928882)). 집중 타이머에서는 바로 그 '빈 시간'이 제품이다. HUD는 Oolite의 Dangerous HUD처럼 알릴 것이 없으면 사라지게 한다 ([Alioth wiki](https://wiki.alioth.net/index.php/Dangerous_HUD)). 진행 상황은 막대 대신 빛으로 보여 준다. Gravity의 라이트 박스는 196개 LED 패널로 궤도 위치에 따라 배우 얼굴에 닿는 빛을 바꿨다 ([LEDinside](https://www.ledinside.com/node/19783)). 같은 발상으로 주변광 색온도를 지구의 청색에서 목적지 색(화성 황토, 금성 연금색, 해왕성 청록)으로 세션 내내 아주 천천히 옮긴다. 5~15분마다 '달 궤도 통과', '소행성대 통과' 같은 표식을 소리도 팝업도 없이 지나가게 하면, Elite 플레이어들이 원했던 항로 비컨의 조용한 버전이 된다. 90분을 장면 단위로 연출할 수는 없다. Active Theory v4가 반복되는 지오메트리 다섯 개로 '끝없는 여정'을 만들었듯 ([Awwwards](https://awwwards.com/active-theory-v4-wins-january-2018-site-of-the-month.html)), 천천히 변하는 환경 몇 개를 이음매 없이 반복하면 된다. 이 기준에서 보면 현재 순항 내내 깔리는 '잔잔한 워프 줄무늬'(가산 블렌딩 LineSegments 170개)와 '가끔 지나가는 플라이바이'는 순항에서 빼서 전환과 마일스톤으로 옮길 후보다. 2001: 스페이스 오디세이는 초연 때 느리다는 불만 탓에 17분을 잘라 냈다 ([NASA History](https://www.nasa.gov/history/50-years-ago-1968-welcomed-2001/)). 하지만 집중 타이머는 그 느림을 원한다.

전환은 이야기가 다르다. 주의를 끄는 것이 목적인 순간이기 때문이다. 탑승권 단계에서는 목적지(과목 행성), 할 일, 시간 프리셋을 고르고, 원하면 '딴생각이 나면 나는 ___한다' 한 줄을 적게 한다. if-then 형식의 실행 의도는 94개 검증에서 목표 달성에 d=0.65의 효과를 보였다 ([Konstanz repository](https://kops.uni-konstanz.de/handle/123456789/69905)). 이미 있는 발사 카운트다운은 3~4초로 줄이고 건너뛸 수 있게 다듬는다. 순서는 이렇다. HUD를 30%로 낮추고, T-3·T-2·T-1을 타이머 뒤에 8% 불투명도의 유령 숫자로 띄운다. 점화 순간 헤어라인 괄호를 400ms에 걸쳐 그리고, HUD 요소를 40~60ms 간격으로 차례로 등장시킨 뒤 타이머가 마지막 주인공으로 들어온다. 워프는 출발과 도착의 1~3초에만 쓴다. Trumbull이 2001의 스타게이트를 위해 만든 슬릿스캔은 한 장면에 약 85번의 노출을 겹친 '이행'의 기술이지, 계속 유지되는 '상태'가 아니다 ([Wikipedia: Douglas Trumbull](https://en.wikipedia.org/wiki/Douglas_Trumbull)).

메인 ↔ 비행 전환에는 View Transitions를 쓴다. same-document 전환은 2025년 10월 Firefox 144가 지원하면서 Baseline이 됐다 ([web.dev](https://web.dev/blog/same-document-view-transitions-are-now-baseline-newly-available)). 이걸 쓰면 포스터 레이아웃의 타이머가 비행 HUD 좌하단으로 모프하는 장면을 적은 비용으로 만들 수 있다. 다만 지금처럼 두 페이지가 별도 HTML이면 cross-document 전환이 필요한데, 이것은 Chromium에서만 확인됐다. 숫자 전환은 NumberFlow처럼 `tabular-nums`로 자릿수 폭을 고정하고, 카운트다운은 `trend=-1`로 항상 아래로 굴린다. 1초마다 바뀌는 숫자에는 튀는 스프링을 쓰지 않는다. NumberFlow는 기본적으로 사용자의 동작 감소 설정을 존중한다 ([NumberFlow](https://number-flow.barvian.me/)). GSAP은 발사·도착 타임라인처럼 순서가 복잡한 곳에만 쓰면 되고, Webflow 인수 이후 SplitText까지 전부 무료가 됐다 ([Webflow](https://webflow.com/blog/gsap-becomes-free)). `prefers-reduced-motion: reduce`에서는 이 모든 연출을 200ms 크로스페이드로 바꾼다 ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)).

도착은 이 앱의 클라이맥스다. 먼저 앰비언스를 끊어 완전한 정적을 만든다. 그다음 그 순간의 비행 프레임을 휘도 3~5단 포스터로 바꾸고, 행성별 레터링과 짧은 과학 캡션(거리, 하루 길이, 온도)을 얹은 카드로 내놓는다. JPL 포스터가 과학자의 검수로 무게를 얻었듯, 짧은 사실 캡션은 움직임 없이도 격을 올린다. 이어서 세 가지를 묻는다. 집중 평점(1~5), '무엇을 끝냈나'(할 일 자동 체크), '다음 한 걸음'이다. 마지막 질문은 Leroy & Glomb의 '재개 준비 계획'에서 왔다. 멈춘 지점과 다음 할 일을 1분 정도 적어 두면 주의 잔여가 줄고 다음 과제의 수행이 좋아졌다 ([UW News](https://www.washington.edu/news/2018/01/16/task-interrupted-a-plan-for-returning-helps-you-move-on/)). 이 메모는 다음 탑승권에 미리 채워 넣는다. 중간에 포기한 비행은 지우지 말고 '지구 귀환'으로 정직하게 기록한다. Forest는 죽은 나무를 숲에 그대로 남기고, 수치심을 주는 표현은 쓰지 않는다 ([Forest](https://forestapp.cc/llms-full.txt)). 휴식은 '관측 갑판'으로 꾸민다. 어떤 휴식 일정이 최선인지는 근거가 갈린다. 87명을 대상으로 한 연구에서 정해진 휴식은 자율 휴식과 같은 성과를 더 짧은 시간에 냈다 ([PubMed](https://pubmed.ncbi.nlm.nih.gov/36859717/)). 하지만 2025년 후속 연구는 Pomodoro, Flowtime, 자율 휴식 사이에서 전체 피로·동기의 차이를 찾지 못했다 ([MDPI](https://www.mdpi.com/2076-328X/15/7/861)). 그러니 25/5, 50/10, 자유 순항을 모두 두는 편이 낫다. 그리고 네 번째 비행 뒤의 '정거장 급유' 긴 휴식이 실제로 발동하는지 꼭 확인해야 한다.

소리는 '우주의 소리'가 아니라 환경의 소리여야 한다. Interstellar 사운드 팀은 가짜 신스 노이즈와 디지털 휙 소리를 배제했고 ([The Sound Architect](https://thesoundarchitect.co.uk/?p=3321)), Zimmer는 템플 교회의 1926년산 오르간으로 길게 이어지는 화음을 썼다 ([Wikipedia](https://en.wikipedia.org/wiki/Interstellar_(soundtrack))). 기본값은 근거에 맞춰 조심스럽게 잡는다. 배경 소음, 말소리, 음악은 모두 읽기에 작지만 일관된 부정 효과를 냈고, 알아들을 수 있는 말과 가사가 가장 방해가 됐다 ([Perspectives on Psychological Science](https://www.psychologicalscience.org/journals/perspectives/1745691617747398/)). 백색·분홍 소음은 ADHD 집단에는 g=0.249의 작은 이득을 줬지만, 비ADHD 집단에서는 g≈−0.21로 오히려 손해였다. 갈색 소음 연구는 하나도 없다 ([Nigg et al. 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11283987/)). 바이노럴 비트는 EEG 연구 14개 중 5개만 뇌파 동조를 지지했다 ([PLoS ONE review](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10198548/)). 그래서 사운드는 기본으로 꺼 두거나 첫 실행 때 한 번 묻고, 낮은 음량에서 시작한다. 캐빈 험은 AudioWorklet에서 갈색·분홍 소음을 만든 뒤 200~600Hz 저역 통과 필터와 수 초 주기의 느린 게인 변화를 거쳐 만든다. 갈색 소음은 백색 소음을 누설 적분해서, 분홍 소음은 Paul Kellet 필터로 얻는다 ([Software Mansion](https://docs.swmansion.com/react-native-audio-api/docs/guides/noise-generation); [MDN AudioWorklet](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorkletProcessor)). 효과음은 점화 스웰, 카운트다운 틱, 휴식 시작 벨, 도착 차임, 선택적 UI 블립까지 3~5개면 충분하다. 모든 소리는 화면의 사건과 짝을 이뤄야 한다. 장식용 소리를 줄이라는 Material의 지침과 같은 방향이다 ([Material Design](https://m2.material.io/design/sound/applying-sound-to-ui.html)). 바이노럴 '뇌파' 모드를 넣는다면 '실험적·취향'이라고 표시한다.

## HUD와 통계는 세 계층·세 선굵기·하나의 신호색으로 정리한다

영화 UI 스튜디오들의 원칙은 한 줄로 모인다. Territory Studio의 David Sheldon-Hicks는 화면 그래픽이 이야기를 '가로채지 않고 받쳐야' 한다고 말한다. 먼저 어떤 콘텐츠가 흐르는지 정하고, 시각 스타일은 그 위에 '필터'로 씌운다는 것이다 ([Pushing Pixels](https://www.pushing-pixels.org/2014/08/07/the-craft-of-screen-graphics-and-movie-user-interfaces-interview-with-david-sheldon-hicks-of-territory-studio.html)). Jayse Hansen은 화면의 모든 요소가 기능을 가져야 하고 장식에 그쳐서는 안 된다고 했다 ([hudsandguis](https://www.hudsandguis.com/2013/05/15/the-avengers/)). GMUNK의 Oblivion 브리프는 어두운 배경과 밝은 배경 모두에서 읽히는 하나의 통일된 팔레트를 요구했다 ([ProVideo Coalition](https://www.provideocoalition.com/hud-and-gui-graphics-in-oblivion/)). 우주뽀모도로로 옮기면 HUD는 세 계층으로 고정된다. T1은 화면당 하나뿐인 타이머 숫자(15~25vh), T2는 미션 이름과 단계(Pretendard 14~16px), T3는 모노 10~11px 대문자 텔레메트리다. 텔레메트리에는 가짜 좌표나 무작위 16진수를 넣지 않는다. 남은 시간, N/M번째 세션, 오늘의 순공 시간, 이번 주 목표, 이동 거리, 다음 휴식까지 남은 시간처럼 실제 데이터만 넣는다. 선 굵기도 세 가지로 묶는다. 1px·10~20% 알파의 헤어라인, 1px·30~40% 알파의 구조선, 2px 신호색 진행선이다. 신호색은 지금의 주황(#ff5b1f)을 그대로 쓰되 '지금 살아 있는 상태'에만 쓴다. 중단과 오류는 별도의 빨강으로 구분한다. 과목 색은 OKLCH에서 명도와 채도를 같게 맞추고 색상만 약 60° 간격으로 벌린다. 그래야 어느 과목도 다른 과목보다 튀지 않는다.

글꼴은 갈아엎을 필요가 없다. 현재 코드는 이미 Inter Tight(디스플레이), Pretendard Variable 동적 서브셋(본문), IBM Plex Mono(텔레메트리), Archivo(통계 숫자)를 쓰고 있고, 이는 연구가 권한 무료 스택과 거의 같다. Pretendard는 Latin 글리프를 Inter에서 가져왔기 때문에 Inter 계열 숫자와 형태·메트릭이 맞는다. 라이선스는 SIL OFL이고 동적 서브셋도 제공한다 ([GitHub Pretendard](https://github.com/orioncactus/pretendard)). 손볼 것은 세부다. 타이머를 지금의 굵기 500에서 200~300으로 낮추면 큰 크기에서 고급스럽고 차분하게 읽힌다. 굵은 숫자는 스포티하게 읽힌다는 것이 연구 노트의 판단이다. Inter 4는 옵티컬 사이즈 축(`opsz`)이 있어서 HUD 타이머와 전체 화면 타이머 사이를 축 하나로 오갈 수 있다 ([rsms.me/inter](https://rsms.me/inter/)). 콜론은 한 단계 가볍게 하고 살짝 올려서 숫자 사이의 광학 중심을 맞춘다. 모노 글꼴을 더 현대적으로 바꾸고 싶다면 OFL에 9개 굵기를 갖춘 Geist Mono가 있다 ([Vercel](https://vercel.com/font)). 피해야 할 글꼴도 있다. Satoshi는 무료지만 OFL이 아니어서 공개 서버에 올려 재배포하는 것을 막는다 ([Adom LICENSES.md](https://wiki.adom.inc/adom/adom-theme/files/fonts/LICENSES.md)). PP Neue Machina 체험판은 비상업용이다 ([LicenseOrg](https://licenseorg.com/guide/fonts/pangram-pangram)). 한글 제목과 라벨에는 `word-break: keep-all`과 `text-wrap: balance`를 함께 건다. `keep-all` 없이 `balance`만 쓰면 어절 중간에서 줄이 끊길 수 있다 ([daleseo.com](https://daleseo.com/css-text-wrap/)).

3D 장면 위의 글자는 WCAG 1.4.3의 4.5:1(큰 글자는 3:1)을 '배경에서 가장 밝은 픽셀' 기준으로 지켜야 한다. 이미지, 그라디언트, backdrop-filter 위의 텍스트도 예외가 아니다 ([Acquia](https://docs.acquia.com/web-governance/text-top-image-gradient-or-backdrop-filter-should-have-minimum-contrast)). 텍스트 그림자는 믿을 만한 대비 해법이 아니다 ([Smashing Magazine](https://smashingmagazine.com/2023/08/designing-accessible-text-over-images-part1)). 화면 전체를 어둡게 하는 대신 HUD 모서리마다 방사형 스크림을 깐다. 40% 정도의 검정 그라디언트에서 시작해 실제로 측정하며 조정한다 ([UX Collective](https://uxdesign.cc/techniques-to-display-text-over-background-images-b089de1cc8bc)). 카메라 구도는 태양, 행성 가장자리, 엔진 불꽃이 HUD 모서리에 들어오지 않게 잡는다. 10~11px 텔레메트리를 50% 알파로 두면 완전히 어두운 배경이 아닌 곳에서 대비가 무너지므로 60~70% 이상으로 올린다. 할 일 목록은 움직이는 배경 위에 두지 않는다. 텍스트 옆에서 무언가가 움직이면 고정과 되돌아 읽기가 늘기 때문이다. 다크 모드가 기본이어도 읽기용 라이트 표면은 선택지로 둘 만하다. 교정 과제에서는 밝은 바탕에 어두운 글자가 젊은층과 노년층 모두에게 유리했다 ([NN/g](https://www.nngroup.com/articles/dark-mode/)). 포스터·인쇄물 은유에서는 종이색 테마가 오히려 자연스럽다. 지금 칩과 도착 오버레이에 쓰인 `backdrop-filter: blur()`는 작은 면적이라면 괜찮다. 다만 글자가 블러에만 기대지 않도록 50~70% 불투명 바탕을 함께 깐다.

통계 바는 한국 사용자에게 가장 민감한 화면이다. 열품타는 App Store 한국에서 약 4.8만 개 평가에 4.5점, 교육 분야 10위다. 최근 리뷰에는 두 가지 불만이 두드러진다. 플래너 중심의 새 홈이 큼직하던 '오늘 총 공부 시간'과 과목별 합계를 묻어 버렸다는 것, 그리고 수동으로 넣은 시간이 그룹·랭킹 합계에 섞이기 시작했다는 것이다. 개발사는 결국 '클래식' 화면을 되살리는 선택지를 넣었다. 같은 앱에서 '공부할수록 진해지는 달력'은 칭찬받는 장치다 ([App Store KR](https://apps.apple.com/kr/app/%EC%97%B4%ED%92%88%ED%83%80/id1441909643)). 여기서 A안 통계 바에 대한 결론이 나온다. '오늘 순공 시간'을 T1급 큰 숫자로 고정하고, 행성(과목)별 분할을 바로 옆에 둔다. 기록은 타이머가 잰 시간만 집계하고, 수동 보정은 표시해서 따로 분리한다. 스트릭은 매일이 아니라 주간 목표('이번 주 5회 비행')로 바꿔 불안을 줄인다 ([Smashing Magazine](https://smashingmagazine.com/2026/02/designing-streak-system-ux-psychology/)). 히트맵은 한 색상의 5단 명도로 칠한 정사각 셀로 만들고, Cal-Heatmap(MIT)이나 직접 짠 SVG로 구현한다 ([npm](https://npmjs.com/package/cal-heatmap)). 진행 원형은 두꺼운 도넛 차트보다 5분마다 눈금이 있는 1~2px 시계 베젤형 링이 '미션 클록'에 어울린다. 게임 요소는 얇게 유지한다. Habitica가 받은 비판은 게임 요소가 그 자체로 또 하나의 게임이 되어 버린다는 것이었다 ([Makerstack](https://makerstack.co/reviews/habitica-review/)).

## 결론

이번 조사로 이해가 달라진 지점은 세 가지다. 첫째, 이 앱에서 성능 작업과 디자인 작업은 같은 일이다. 지금 GPU는 변하지도 않는 행성 표면을 매 프레임 다시 계산하는 데 쓰이고 있고, 그 시간을 굽기로 되찾아야 대기 산란, 그레이딩, 안티앨리어싱을 '발열 없이' 들여올 수 있다. 0단계를 건너뛰고 2단계로 가면 더 예뻐진 장면이 노트북을 더 뜨겁게 만들고, 사용자는 30분 만에 탭을 닫는다. 둘째, 집중 앱의 '멋'은 밀도가 아니라 대비에서 나온다. 89분의 고요가 있어야 4초의 발사와 도착이 극적이 되고, 순항의 정적은 결함이 아니라 연출이다. 셋째, 경쟁 앱에 없는 연결 고리는 포스터다. 메인 페이지의 인쇄물 미학이 도착 보상과 수집으로 이어지면, 두 페이지는 '계획하는 곳'과 '날아가는 곳'으로 갈리지 않고 하나의 항해 일지가 된다. 남은 불확실성도 분명하다. 3D 우주 배경이 공부에 득인지 실인지 직접 검증한 연구는 없고, fps 상한과 베이킹의 절감 효과도 측정이 아니라 산술이다. 그러니 모든 시각 요소는 끌 수 있어야 하고, 단계마다 실제 노트북에서 전력과 GPU 사용률을 재며 나아가야 한다.

0단계 루프의 골격은 다음과 같다(r160, 추가 import 없음). 기존 코드의 `requestAnimationFrame(frame)`을 이 구조로 바꾸고, `update` 안의 모든 이동량을 `속도 × step`으로 고친다.

```js
let targetFps = 30, last = 0, acc = 0;          // 전환·조작 중 60, 집중 30, 차분 15~20
function loop(t) {
  const dt = Math.min((t - last) / 1000, 0.1); last = t; acc += dt;
  const frame = 1 / targetFps;
  if (acc < frame * 0.95) return;               // 이번 콜백은 건너뜀(거의 공짜)
  const step = acc; acc %= frame;
  update(step);
  composer.render(step);
}
renderer.setAnimationLoop(loop);
document.addEventListener('visibilitychange', () => {
  if (document.hidden) renderer.setAnimationLoop(null);
  else { last = performance.now(); renderer.setAnimationLoop(loop); }
});
```

### 핵심 리스크

| 리스크 | 왜 생기나 | 완화책 |
|---|---|---|
| 렌더링 개선이 절감분을 다시 먹는 발열 회귀 | 대기 셸, MSAA, 플레어는 모두 픽셀 비용이다 | 효과마다 티어 게이팅; 단계 전후로 작업 관리자 GPU %·전력 A/B; 티어 2에서 30fps를 못 지키는 효과는 High 전용으로 |
| 라이브러리 버전 충돌 | pmndrs 6.36.0은 three ≥ 0.157, < 0.168만 지원하고, `+esm`은 three 중복 로드 위험이 있다 | 버전 고정, 패키지 자체 ESM 빌드 사용, AGX·NEUTRAL 모드 존재를 먼저 확인 |
| r160 AgX 품질 | 색역 수정이 r161에 들어왔다 | r167로 올리거나, r160을 유지한다면 ACES + LUT |
| 검증되지 않은 절감 수치 | 베이킹·fps 상한의 효과는 산술 추정이고 공개 벤치마크가 없다 | 직접 측정한 값만 근거로 삼고, 측정 전에는 수치를 약속하지 않음 |
| 과자극 | '100배'라는 압력 때문에 전환이 길어지고 순항에 이벤트가 붙는다 | 전환 길이 상한(발사 ≤ 4초, 워프 ≤ 3초), 건너뛰기, reduced-motion, '순항 중 사건 0건' 규칙 |
| 라이선스 | Shadertoy 기본 CC BY-NC-SA 3.0, Satoshi 재배포 제한, Solar System Scope 출처 표기 의무 | Shadertoy는 참고만 하고 재구현; OFL·CC0·MIT 우선; 크레딧 화면 |
| 긴 세션 안정성 | 90분 동안 누수나 WebGL 컨텍스트 손실이 생길 수 있다 | `renderer.info` 주기 로그, `webglcontextlost` 처리, 다시 실행 가능한 베이크, 프레임마다 객체 생성 금지 |
| 기기 판별 오류 | detect-gpu 데이터가 2025년 12월 이후 갱신되지 않는다 | 모르는 GPU는 티어 2 + 런타임 모니터, 사용자 설정을 최우선으로 |
| 게임 요소 비대화 | 수집·보상이 과제와 주의를 다툰다 | 수집은 실제 집중 분과 1:1로, 미니게임 금지 |
| 페이지 분리 구조 | 메인과 비행이 별도 HTML이면 same-document View Transitions를 쓸 수 없다 | 한 문서로 통합하거나, cross-document 전환(Chromium)에 즉시 전환 폴백 |
| 단일 파일 비대화 | 텍스처·사운드·모델을 넣을수록 파일이 커지거나 CDN 의존이 늘어난다 | 결정 8에서 범위를 확정하고, 절차적 생성을 우선 |
