# Real-time WebGL/Three.js Techniques for Cinematic Space Scenes (Cosmodoro, Three.js r160, no build step)

> Scope note for the report writer: "Cited Findings" are things verified from a source during this research session (October 2026). "Inferences" are engineering judgments, implementation recipes and GPU-cost estimates built on those findings plus general graphics knowledge. They are labeled as such and were not benchmarked. Shadertoy code is CC BY-NC-SA 3.0 by default, which affects reuse (see Q1/Q3).

## Q1. Atmospheric scattering for planets: what is practical in a fragment shader on a sphere for web, and are there Three.js implementations?

### Takeaway
For Cosmodoro the practical choice is a **single-pass, analytic/ray-marched Rayleigh+Mie(+ozone) shader on the existing atmosphere shell or in a screen-space pass**, with low step counts (about 8-16 primary, 4-8 light) or a small transmittance LUT. The main off-the-shelf Three.js library (takram `@takram/three-atmosphere`, Bruneton precomputed) **requires three >= 0.170 and is effectively Earth-only**, so it does not drop into r160. O'Neil (GPU Gems 2 ch.16) is the cheapest "real" option. Hillaire 2020 LUTs are the high-end option, but only GLSL 330/WGSL ports exist, so it needs hand-porting.

### Cited Findings
**takram three-geospatial / three-atmosphere (Bruneton precomputed)**
- `@takram/three-atmosphere` is a Three.js + R3F implementation of Eric Bruneton's precomputed atmospheric scattering, status Beta, MIT licensed — [GitHub atmosphere package](https://github.com/takram-design-engineering/three-geospatial/tree/main/packages/atmosphere)
- Classes: `AerialPerspectiveEffect` (a postprocessing `Effect` applying transmittance + inscatter, optionally sun/sky irradiance with Lambertian BRDF only), `SkyMaterial` (screen-quad sky, sun, moon; "from space it shows Earth's atmosphere above a flat ground"), `StarsMaterial` (~9,096 stars from Yale Bright Star Catalog v5 as points at infinity), `SunDirectionalLight` (samples transmittance on CPU for sun color), `SkyLightProbe`, `LightingMaskPass` — [GitHub atmosphere package](https://github.com/takram-design-engineering/three-geospatial/tree/main/packages/atmosphere)
- Precomputed textures (`transmittanceTexture`, `scatteringTexture`, `irradianceTexture`) are generated at runtime by `PrecomputedTexturesGenerator` (incremental over frames) or loaded via `PrecomputedTexturesLoader` (EXR/binary). Float type falls back to half float if unsupported. Limitations: reference frame fixed to ECEF, effectively limited to Earth's atmosphere, no volumetric light shafts, a horizon artifact can't be fully removed, GLSL only (no TSL/WebGPU yet). A vanilla (non-React) example exists — [GitHub atmosphere package](https://github.com/takram-design-engineering/three-geospatial/tree/main/packages/atmosphere)
- **Version blocker:** package v0.19.1 has peerDependencies `three >= 0.170.0` and `postprocessing >= 6.36.7`. It also depends on `@takram/three-geospatial`, `astronomy-engine` and others — [jsDelivr package.json](https://cdn.jsdelivr.net/npm/@takram/three-atmosphere/package.json)
- The project started as a prototype for Eukarya's Web GIS engine under Japan's SBIR program. Takram's contribution ended March 2025. The maintainer says WebGPU support needs a full API rewrite (moving from shader chunks to nodes) — [Trendshift summary](https://trendshift.io/admin/repository/ask-ai/13111); [Takram project page](https://www.takram.com/projects/three-geospatial)

**Sean O'Neil, GPU Gems 2 ch.16 (analytic, cheapest)**
- O'Neil removes the 2D optical-depth lookup table with a closed-form fit: normalized optical-depth curves follow exp(-4x) in height, and a fitted polynomial "scale function" covers angle — "we eliminate the lookup table without sacrificing image quality" — [NVIDIA GPU Gems 2 ch.16](https://developer.nvidia.com/gpugems/gpugems2/part-ii-shading-lighting-and-shadows/chapter-16-accurate-atmospheric-scattering)
- The baseline is about 5 in-scattering samples plus 5 per out-scattering integral (~300 ops/vertex). The shader version cuts out-scattering to about 1 sample each for sun and camera rays. In-scattering runs in the vertex shader (SkyFromSpace.vert outputs Rayleigh and Mie colors). The phase function runs in the fragment shader to avoid tessellation artifacts. There are separate shader variants per "object From camera-position" (SkyFromSpace, GroundFromSpace, etc.) to avoid branching — [NVIDIA GPU Gems 2 ch.16](https://developer.nvidia.com/gpugems/gpugems2/part-ii-shading-lighting-and-shadows/chapter-16-accurate-atmospheric-scattering)
- Limitations: the scale function is fit to scale height = 25% of atmosphere thickness and atmosphere = 2.5% of planet radius ("you need to calculate a new scale function" if changed). Single scattering only. The Rayleigh phase is disabled because it darkens the sky near 90°. Sun is the only light. HDR is needed — [NVIDIA GPU Gems 2 ch.16](https://developer.nvidia.com/gpugems/gpugems2/part-ii-shading-lighting-and-shadows/chapter-16-accurate-atmospheric-scattering)

**Single-pass ray-marched (Nishita-style) and Hillaire 2020 LUTs in WebGL**
- Maxime Heckel (May 2026) implements atmosphere as a full-screen post-process in R3F. It reconstructs world rays from depth (`projectionMatrixInverse`, `viewMatrixInverse`), uses `logarithmicDepthBuffer: true`, and does two ray-sphere intersections (atmosphere radius, planet radius) clipped by scene depth. `PRIMARY_STEPS = 24` with a nested light march — [Maxime Heckel blog](https://blog.maximeheckel.com/posts/on-rendering-the-sky-sunsets-and-planets/)
- Heckel's Earth-like coefficients: Rayleigh scale height 8 km, β = (0.0058, 0.0135, 0.0331), phase 3/(16π)(1+μ²). Mie scale height 1.2 km, β_scatter = 0.003. Ozone β_abs = (0.00065, 0.00188, 0.00008). Atmosphere height 100 km. Mars preset: Rayleigh β ≈ (0.019, 0.013, 0.0057), scale height 11.1, mieG 0.65, no ozone — [Maxime Heckel blog](https://blog.maximeheckel.com/posts/on-rendering-the-sky-sunsets-and-planets/)
- Heckel's partial Hillaire-2020 port in WebGL: a 250×64 transmittance LUT replaces the nested light march, plus a sky-view LUT (quadratic elevation mapping) and a screen-sized 2D aerial-perspective target instead of the paper's 3D texture. Multi-scattering was skipped. He reports a "non-negligible speedup" but also banding/flicker in the sky-view LUT, and suggests WebGPU compute as the better path — [Maxime Heckel blog](https://blog.maximeheckel.com/posts/on-rendering-the-sky-sunsets-and-planets/)
- Hillaire's paper (CGF 2020, vol. 39 no. 4) does not require high-dimensional LUTs, which keeps them small for constrained platforms — [Eurographics DL](https://diglib.eg.org/items/8a3e5350-18b3-46bd-9274-3add5af88c75/full); PDF: [sebh.github.io](https://sebh.github.io/publications/egsr2020.pdf)
- FlightGear's fgdata has GLSL 330 fragment shaders for all four Hillaire LUTs (transmittance, multiple-scattering, sky-view, aerial-perspective). This is the closest GLSL source to port to WebGL2 — [FlightGear sky-view.frag](https://git.nayala.duckdns.org/fly/fgdata/src/commit/760db3ba6d7fa4b858dc06feedca848e5b8b88ac/Shaders/HDR/atmos-sky-view.frag); [multiple-scattering.frag](https://git.nayala.duckdns.org/fly/fgdata/raw/commit/83042981460ddab7f3aa44fe9a4a54da00853e34/Shaders/HDR/atmos-multiple-scattering.frag). Bevy has a WGSL version — [Bevy atmosphere mod.rs](https://doc.qu1x.dev/bevy_trackball/src/bevy_pbr/atmosphere/mod.rs.html). pl-sky is an experimental prototype — [hoffstadt/pl-sky](https://github.com/hoffstadt/pl-sky)
- Nishita93 reference parameters: R = 6371 km, atmosphere 80 km, Rayleigh H = 7994 m, Mie H = 1200 m, brute-force view-ray march plus a second march toward the sun — [fgdata atmos.glsl](https://git.nayala.duckdns.org/fly/fgdata/raw/commit/39acfe85e2aade5fe760302b220b85896013ee0f/Shaders/HDR/atmos.glsl) (via search summary)
- Integrating light optical depth analytically removes the inner loop (Blender community shader) — [Blender Artists](https://blenderartists.org/t/planetary-atmospheric-scattering-shader/1283317). Fewes' MinimalAtmosphere (Unity) does Rayleigh+Mie single scattering + ozone in a compact shader — [Fewes/MinimalAtmosphere](https://github.com/Fewes/MinimalAtmosphere)
- Alan Zucconi's tutorial series explains the theory step by step — [Alan Zucconi](https://alanzucconi.com/2017/10/10/atmospheric-scattering-1/)
- Shadertoy shaders are CC BY-NC-SA 3.0 by default, which matters when copying code — [Godot Shaders port note](https://godotshaders.com/?p=6875)

### Inferences
- **Recommended path for Cosmodoro (r160, single HTML):** replace the "additive back-face fresnel shell" with a **ray-marched shell shader** on the same sphere mesh (radius about 1.025 × planet). Per fragment: ray-sphere intersect the atmosphere and planet, then march 8-12 primary samples with an analytic or 4-step light depth. Accumulate Rayleigh+Mie with proper phase functions and output premultiplied HDR (`blending: CustomBlending` with One/OneMinusSrcAlpha, or additive with transmittance applied in the surface shader). Also apply the same scattering to the **planet surface shader** (aerial perspective + sunset terminator tint). This gives the "blue limb + orange terminator + forward-scattering halo when backlit" look, the biggest realism jump over fresnel.
- **Cost estimate:** a shell-only pass touches only planet-covered pixels. At 12×6 samples that's roughly 72 density evaluations/pixel. Fine on discrete/Apple-silicon laptops at 1080p. On integrated Intel or mobile, drop to 6×3 samples or render the shell into a half-resolution target. A 256×64 transmittance LUT (rendered once to a `WebGLRenderTarget` with `HalfFloatType`) removes the inner loop for about 2-4× savings.
- **O'Neil** is the cheapest (vertex-shader work, near-free per pixel) but needs high tessellation and fixed ratios. Good for a "calm, stylized but correct" look on low-end devices.
- **takram** needs three ≥ 0.170 and is Earth/ECEF-centric. Use it as a reference for parameters and code (MIT), not as a drop-in. If the project ever upgrades three (r170+), it becomes viable for an Earth hero planet.
- **Rings:** apply a Mie-like forward-scattering term to the Saturn ring shader (brightness ∝ HG phase with g ≈ 0.6-0.8 when the camera faces the sun through the rings). Add planet-shine and the existing planet shadow. Ring particle backlighting is a strong cinematic cue.
- **Stylization for calm:** keep sun intensity moderate, use a slightly desaturated Rayleigh β for non-Earth planets (e.g., teal/violet worlds), and animate the sun direction slowly or not at all.

## Q2. Better planet surfaces: real texture maps vs procedural, normal/cloud/night/specular layers, ring scattering, gas giant flow/domain-warping

### Takeaway
Use **hybrid**: real CC BY 4.0 maps (Solar System Scope, 2k/8k) for recognizable planets, with procedural detail on top. For fictional worlds and gas giants, use **domain-warped fbm with sine banding and slow time-offset warps** (cheaper than full flow noise). The premium look comes from layering: albedo + normal + specular/roughness mask (oceans) + separate cloud shell casting a shadow + night-lights masked by the terminator + atmosphere.

### Cited Findings
- **Solar System Scope textures** are "Distributed under Attribution 4.0 International license" (CC BY 4.0), usable for any purpose including commercial. Available: Mercury, Venus surface/atmosphere, Mars, Jupiter, Saturn, Saturn ring (PNG alpha), Uranus/Neptune (2k only), Earth Day/Night/Clouds (2k, 8k) + Normal and Specular (2k, 8k, TIF), Sun, Moon, Stars, Stars+Milky Way (2k, 8k), and fictional Ceres/Haumea/Makemake/Eris (2k, 4k) — [Solar System Scope textures](https://www.solarsystemscope.com/textures/)
- NASA 3D Resources says its assets are "free to download and use" and "without copyright", mirrored on GitHub. The official terms point to NASA's general media usage guidelines — [NASA 3D Resources GitHub](https://github.com/nasa/NASA-3D-Resources); [science.nasa.gov 3D resources](https://science.nasa.gov/3d-resources/)
- **Domain warping:** warping distorts the coordinate before sampling. Small amounts give gentle flow, large ones fold the field into a marbled look — [GameDev.net shaderlab: domain warped noise](https://gamedev.net/shaderlab/23-domain-warped-noise/). Warps can be nested ("warp the warp") and animated with time offsets — [skills.sh shader-noise reference](https://skills.sh/bbeierle12/skill-mcp-claude/shader-noise). Canonical reference: Inigo Quilez "Domain warping" [iquilezles.org/articles/warp](https://iquilezles.org/articles/warp/) (page returned 404 to the fetch tool in this session, so contents were not re-verified)
- A commercial Unity procedural-planet framework replaced its gas giant shader with "lower-order domain warping noise" + a vertical sine function for banding, "more than doubl[ing] performance to 140+ FPS at 1080p" — [Unity Discussions](https://discussions.unity.com/t/released-procedural-planet-generation-shaders-in-editor-baking-custom-space-lighting/1700475)
- Other gas giant references: Seed of Andromeda dev blog on real-time GPU-noise gas giants — [ModDB](https://www.moddb.com/news/procedural-gas-giant-rendering-with-gpu-noise). A University of Tartu thesis on velocity-based (simulation) gas giant generation — [UT thesis](https://dspace.ut.ee/items/c79fe79a-29fa-4206-8c43-7fe6b580f48b/full). Blender procedural banding tutorial — [BlenderNation](https://www.blendernation.com/2021/08/11/jupiters-eye-warping-procedural-materials/)

### Inferences
- **Layer stack for a "hero" rocky/ocean planet (recommended):**
  1. Albedo (8k on desktop, 2k on mobile, chosen at runtime by `renderer.capabilities.maxTextureSize` + `navigator.deviceMemory` heuristics).
  2. Normal map in `MeshStandardMaterial`/custom shader for terminator relief. Low-angle sun across the normal map sells scale.
  3. Ocean mask → low roughness + sun glint (GGX specular lobe). Add a Fresnel-boosted sky reflection near the limb.
  4. Night lights (emissive) multiplied by `smoothstep(0.1, -0.2, dot(N, L))` so they fade in past the terminator, tinted warm sodium (≈ #ffb46b).
  5. Cloud shell at r × 1.005-1.01, alpha from clouds map, rotating slightly faster than the surface. **Cloud shadows:** in the surface shader, sample the cloud texture at UV offset along the sun direction projected to tangent space (`uv - L_tangent.xy * k`), then darken albedo. Costs 1 extra texture fetch.
  6. Atmosphere (Q1).
- **Gas giants:** latitude-band function `bands = sin(lat * N + fbm(p*2)*warp)` → 1D color ramp texture (sample a 256×1 gradient, easy to art-direct). Add 2-level domain warp `q = fbm(p + t*0.01)`, `r = fbm(p + 4q)`. Add zonal shear (rotate longitude by a latitude-dependent speed, `lon += t * speed(lat)`, which gives a jet-stream look). Add storm ovals as warped gaussian blobs. Better still, **bake to an equirect texture** in a render target once (or every N seconds) and sample it on the sphere. This cuts the per-frame fbm cost to near zero, which matters for laptops running for 25-minute sessions.
- **Flow noise** (Perlin & Neyret 2001, rotating-gradient noise) gives "swirling but not advecting away" motion, ideal for calm loops. A cheaper approximation is two-phase flow mapping (sample warped field at t and t+0.5 and crossfade, as in water flowmaps), which avoids long-run smearing.
- **Procedural normal from fbm:** compute the height gradient by finite differences (3-4 extra noise evaluations) or analytic-derivative noise (IQ's noise derivatives) to bump-light procedural planets. This is a big upgrade from flat-lit fbm color.
- **Ring scattering:** ring texture alpha → optical depth. Back-lit brightness ∝ HG(g≈0.7). Planet-shadow cone already exists. Add ring shadow on the planet by projecting the ring plane along the light direction in the planet shader (ray-plane intersect, sample ring alpha). That's 1 texture fetch, high payoff.
- **Licensing:** CC BY 4.0 requires attribution (credits screen line "Planet textures: Solar System Scope, CC BY 4.0"). NASA imagery is generally free, but NASA logos/insignia have separate restrictions (not verified here).
- **Compression:** convert 8k JPG maps to KTX2 (UASTC for normals, ETC1S for albedo/clouds) to cut GPU memory about 4-8× and upload time (see Q5 for loader setup).

- Did not verify NASA Visible Earth (Blue Marble / Black Marble) download resolutions and exact usage terms in this session.
- No source measured cloud-shadow or ring-shadow cost in WebGL. Estimates above are mine.
- Flow-noise original paper (Perlin & Neyret, SIGGRAPH 2001 sketch) was not fetched.

## Q3. Volumetric nebulae/galaxies, better star fields, lens flares, chromatic aberration, grain, vignette, anamorphic streaks, god rays

### Takeaway
For a calm study app, **don't ray-march nebulae every frame at full resolution**. Either (a) bake a higher-quality volumetric/ray-marched nebula into the cube-map sky once at load (offline-quality look for zero per-frame cost), or (b) ray-march at quarter/half resolution inside a bounded sphere with a 3D noise texture and blue-noise jitter. Stars improve most from **physically plausible color (blackbody) and magnitude distribution, no twinkle in space, and a few hero stars with soft diffraction spikes**. Lens effects should be subtle: the ektogamat CC0 vanilla lens flare plus pmndrs Vignette/Noise/ChromaticAberration at low intensity.

### Cited Findings
**Nebulae / volumes**
- Gaia Sky renders nebulae as a full-screen-quad post-process ray march: setup (ray, camera/object positions, depth lookup) → fixed-step march accumulating density and color → blending. A ray-sphere bounding volume, depth-buffer sampling for mutual occlusion, mostly alpha blending — [Toni Sagristà, Gaia Sky blog](https://tonisagrista.com/blog/2024/rendering-aurorae-nebulae/)
- Gaia Sky's nebulae (Cat's Eye, Hourglass, Trifid, Butterfly, Crab) were adapted from Duke's Shadertoy "Dusty Nebula 4" and "Supernova Remnant", which are **CC BY-NC-SA 3.0** — [Gaia Sky blog](https://tonisagrista.com/blog/2024/rendering-aurorae-nebulae/)
- A three.js single-HTML-file volumetric cloud generator bakes FBM density "into a 3D texture on the fly" and ray-marches it in GLSL with scattering/absorption. Code at GitHub leoawen/volumetric-clouds — [three.js forum: volumetric clouds](https://discourse.threejs.org/t/volumetric-clouds-game-ready/86598.md)
- A R3F ray-marching template warns ray-marching shaders are "too GPU-intensive for most mobile devices" — [rapidevelopers template](https://rapidevelopers.com/v0-template/react-three-fiber-ray-marching)
- Godot volumetric nebula shader (a starting point, not production) — [godotshaders](https://godotshaders.com/shader/volumetric-nebulae-clouds)
- Gaussian splatting in three.js: `@mkkellogg/gaussian-splats-3d` (GaussianSplats3D) supports 3DGS, added spherical harmonics (v0.4.0) and 2DGS (v0.4.3) — [GitHub](https://github.com/mkkellogg/GaussianSplats3D); [radiancefields.com](https://radiancefields.com/three-js-based-implemetation-gaussiansplats3d-adds-2dgs-support)

**Stars**
- Star color matters most for point stars. Most stars should be sub-pixel with widely varying brightness. **Twinkling is atmospheric, so it shouldn't appear in space views** — [Khronos forum](https://community.khronos.org/t/what-is-the-best-most-realistic-method-of-rendering-a-starfield/14296)
- Common recipe: spectral class → blackbody temperature → RGB, magnitude-based brightness, soft radial point sprites, bloom — [skills.cat procedural stars](https://skills.cat/skills/ck42bb/procedural-stars-threejs); [Blender Blackbody node](https://docs.blender.org/manual/en/4.1/render/shader_nodes/converter/blackbody.html); [ModDB procedural star rendering](https://www.moddb.com/news/procedural-star-rendering)
- NASA WebWorldWind's StarFieldProgram passes magnitude as a vertex attribute to modulate point brightness — [WorldWind StarFieldProgram](https://worldwind.arc.nasa.gov/autodocs/WebWorldWind/shaders_StarFieldProgram.js.html)
- takram's `StarsMaterial` uses ~9,096 Yale Bright Star Catalog v5 stars as points at infinity, a real-sky dataset option — [takram atmosphere](https://github.com/takram-design-engineering/three-geospatial/tree/main/packages/atmosphere)

**Lens flare / lens effects**
- ektogamat "lensflare-threejs-vanilla": a scene object (`scene.add(LensFlareEffect())`) with no post-processing pipeline, internal raycaster occlusion (`userData.lensflare = 'no-occlusion'` to exclude). Requires WebGL2, recommends three r153+, **CC0-1.0**. Uniforms: `glareSize`, `flareSize`, `haloScale`, `ghostScale`, `flareShape`, `starPoints` (0-9), `starBurst`, `anamorphic`, `secondaryGhosts`, `flareSpeed`, `animated`. Warning: `starBurst` "is very demanding on some GPUs" — [GitHub ektogamat](https://github.com/ektogamat/lensflare-threejs-vanilla)
- The R3F version (react-postprocessing `LensFlare`) is based on ektogamat/R3F-Ultimate-Lens-Flare — [react-postprocessing docs](https://react-postprocessing.docs.pmnd.rs/effects/lensflare)
- three.js's built-in `Lensflare` addon works only with WebGLRenderer. `LensflareMesh` is for WebGPURenderer — [three.js Lensflare docs](https://threejs.org/docs/pages/Lensflare.html)
- pmndrs postprocessing provides `GodRaysEffect`, `ChromaticAberrationEffect`, `NoiseEffect` (grain), `VignetteEffect`, `LensDistortionEffect`, and `EffectPass` "automatically organizes and merges any given combination of effects" into fewer render operations — [pmndrs docs](https://pmndrs.github.io/postprocessing/public/docs/variable/index.html); [GitHub pmndrs/postprocessing](https://github.com/pmndrs/postprocessing)

### Inferences
- **Nebula plan A ("bake once", recommended for calm):** at startup (or in an idle callback), render a ray-marched nebula into each of the 6 cube faces of the existing baked sky (`WebGLCubeRenderTarget` + a full-screen quad per face, 64-128 steps, 3D-noise or 4-octave fbm with domain warp, emission + absorption, Henyey-Greenstein lit by 1-2 embedded "stars"). Cost: a one-time ~100-500 ms on laptops (estimate). Per-frame cost: one cube sample (already paid). Downside: no parallax. Fine for distant nebulae, and it matches the user's static-sky architecture.
- **Nebula plan B (parallax hero nebula):** bounded sphere, quarter-res ray march (32-48 steps) with blue-noise jitter + temporal accumulation (since the camera moves slowly), bilateral upsample, and alpha-composite before bloom. Estimated cost: 1-3 ms on a mid laptop GPU at 1080p. Skip on mobile (fall back to plan A).
- **Nebula plan C (cheap parallax):** 20-60 large camera-facing billboards with soft noise textures, additive with low alpha, sorted back-to-front, slowly rotating UVs. Very cheap and "painterly". Combine with A for depth.
- **Stars upgrade recipe:** (1) generate N≈20-40k stars with a power-law magnitude distribution (many faint, few bright). (2) color from a blackbody LUT (2,500-30,000 K) weighted toward K/M (orange) for realism. (3) render as points with size ∝ 10^(-0.4·m) clamped to ≥1 px, using a Gaussian PSF in the fragment shader. For sub-pixel stars, fade alpha rather than size (avoids shimmering). (4) output HDR brightness so only the brightest ~0.5% exceed the bloom threshold. (5) for 5-20 hero stars, add a textured diffraction-spike sprite (4- or 6-point JWST-style, procedural `exp(-k|x|)·exp(-k'|y|)` crosses), rotating with the camera roll only. (6) **no twinkle** (physically right in space and calmer). If any is wanted, use a very slow (>4 s period) ±5% brightness drift on a few stars. (7) optionally use the Yale BSC / HYG catalog (positions + B-V color index) for a "real sky".
- **Milky Way band:** keep the cube-map approach but add a dust-lane absorption layer (dark domain-warped fbm multiplied over the bright band) and color variation (warm core, blue arms). This is what makes photographic Milky Way panoramas look real. Alternatively, use the Solar System Scope "Stars + Milky Way" 8k equirect (CC BY 4.0) as the base and add procedural layers on top.
- **Lens effects for calm:** use the ektogamat flare on the sun only, with `starBurst` off, low `ghostScale`, `anamorphic` on with a mild horizontal streak for a cinematic look. Chromatic aberration offset ≈ 0.0005-0.0015 with radial falloff (edges only). Film grain via NoiseEffect at ~0.03-0.06 opacity with `BlendFunction.OVERLAY` (animated grain at 24 fps feels cinematic, or static grain is calmer). Vignette darkness 0.3-0.5.
- **God rays:** pmndrs `GodRaysEffect` needs a light-source mesh (sun sphere) and does screen-space radial blur. Cheap (≈ 60-100 samples at half res). Useful when the sun peeks past a planet limb or the ship. Use sparingly.
- **Anamorphic streaks:** besides the flare, a cheap custom effect is a horizontally stretched blur of the bright-pass (bloom threshold) buffer at 1/4-1/8 res, tinted blue, added at low intensity.
- **Gaussian splats** are not recommended for this use: large data files, sorting cost, no CDN-friendly "space" assets found. Procedural volume or billboards fit better.

## Q4. Color grading / tone mapping in r160, HDR bloom tuning, TAA/SMAA

### Takeaway
In r160 you have ACES Filmic and a **first, not-yet-fixed AgX** (gamut-mapping fix landed in r161). **Khronos PBR Neutral arrived in r162** (not in r160). The strongest upgrade path without changing three is to adopt **pmndrs `postprocessing@6.36.0`** (peer range three ≥0.157 <0.168, compatible with r160). It gives one merged `EffectPass` with mipmap bloom, `ToneMappingEffect`, `LUT3DEffect` (.cube grading), SMAA, vignette, noise and chromatic aberration, all on a HalfFloat HDR buffer.

### Cited Findings
- AgX first landed in three.js **r160**. A gamut-mapping fix followed in **r161** (PR #27413). The r160 implementation "misses a bit that has been added in r161". Users find AgX less saturated than ACES out of the box, and three.js lacks Blender's "Punchy" look option — [three.js forum: Is AgX implemented correctly?](https://discourse.threejs.org/t/is-agx-tonemapping-implemented-correctly/60609); [PR #27413](https://github.com/mrdoob/three.js/pull/27413)

### Inferences
- **No-build import map (sketch, verify paths):**
  ```html
  <script type="importmap">{ "imports": {
    "three": "https://cdn.jsdelivr.net/npm/three@0.160.0/build/three.module.js",
    "three/addons/": "https://cdn.jsdelivr.net/npm/three@0.160.0/examples/jsm/",
    "postprocessing": "https://cdn.jsdelivr.net/npm/postprocessing@6.36.0/build/index.js"
  }}</script>
  ```
  Use the package's own ESM build (which imports bare `"three"`, resolved by the import map) **rather than `+esm`**. jsDelivr's `+esm` rewriting can pull in a second copy of three (duplicate-instance bugs). Verify the `build/index.js` filename for 6.36.0 before shipping.
- **Tone mapping choice:** for a calm, premium space look, ACES (r160) gives contrast/saturation but hue-shifts bright emissives toward yellow/white. AgX in r160 handles highlights more gracefully (sun, engine glow desaturate naturally) but looks flat and has the pre-r161 gamut issue. Fix that by adding a mild saturation/contrast LUT after it ("punchy" substitute). Khronos Neutral (best for faithful UI-brand colors) needs r162+, or a custom ShaderPass. The PBR Neutral GLSL is about 15 lines and can be copied from the Khronos spec repo (github.com/KhronosGroup/ToneMapping, not fetched this session). Practical recommendation: **AgX + a .cube LUT grade** (teal shadows / warm highlights, slightly lifted blacks for a filmic, calm feel), or upgrade three to ≥ r162 to get native Neutral/fixed AgX.
- **Color grading LUTs:** author a LUT in DaVinci Resolve/Photoshop on a screenshot of the scene, export a 33³ `.cube`, and load it via `LUTCubeLoader` (three addons) → `LUT3DEffect` (pmndrs) or `LUTPass` (three). Cost: one 3D-texture fetch per pixel (negligible).
- **HDR bloom tuning:** render emissives/sun/stars in true HDR (values 2-50), set the bloom threshold ≥1.0 (luminance) so only "hot" pixels bloom, use pmndrs `BloomEffect({ mipmapBlur: true, luminanceThreshold: 1.0, intensity: 0.6-1.2, radius: 0.6-0.85 })` (mip-chain bloom is wider and smoother than UnrealBloomPass), and apply bloom **before** tone mapping. The common "milky haze" problem comes from a low threshold on LDR values.
- **Anti-aliasing:** with a post chain, MSAA on the canvas is lost. Options: (a) pmndrs `EffectComposer({ multisampling: 4 })` (WebGL2 MSAA render target; best for thin ship edges and rings; moderate cost), (b) `SMAAEffect` (cheap, ~0.3-0.6 ms, good for edges, doesn't fix shimmering specular), (c) three's `TAARenderPass` (accumulates jittered frames, which suits a mostly static camera but ghosts on moving particles). For Cosmodoro, **MSAA ×4 + SMAA LOW** or MSAA alone is the robust choice. Also cap DPR: `renderer.setPixelRatio(Math.min(devicePixelRatio, 1.5-2))`.
- **Ordering:** RenderPass → (godrays, nebula composite) → Bloom → ChromaticAberration → ToneMapping(AgX/ACES) → LUT3D → Vignette → Noise(grain) → SMAA (or SMAA before tonemap, depending on edge detection mode), merged into 1-2 EffectPasses.

## Q5. Making a procedural spaceship look premium

### Takeaway
The highest-leverage upgrades are: (1) **image-based lighting** (a CC0 Poly Haven HDRI or a custom "space studio" env map via PMREM) so metals have something to reflect, (2) **proper PBR masks** (roughness/metalness variation, edge wear, panel-line normal detail) instead of flat canvas colors, (3) **strong rim/back light + emissive accents that bloom**, and (4) optionally a **CC0/CC BY glTF hull compressed with Draco/KTX2**. Licensing: Poly Haven is CC0. NASA 3D Resources is free and without copyright. Sketchfab models carry per-model licenses (Standard/Editorial store licenses and CC variants).

### Cited Findings
- Poly Haven: all HDRIs, textures and models are **CC0**, with no attribution required, commercial use and redistribution allowed (site logos/text excluded) — [Poly Haven license](https://polyhaven.com/license)
- NASA 3D Resources (spacecraft models) are "free to download and use" and "without copyright", mirrored at github.com/nasa/NASA-3D-Resources. NASA asks users to report usage to arc-special-proj@lists.nasa.gov — [NASA 3D Resources GitHub](https://github.com/nasa/NASA-3D-Resources); [science.nasa.gov 3D resources](https://science.nasa.gov/3d-resources/)
- Sketchfab Store **Standard** license: royalty-free one-time payment, no sublicensing/standalone resale. **Editorial** license cannot be used for commercial/promotional use. Both require retaining copyright notice/licensor/ID for electronic files — [Sketchfab licenses](https://sketchfab.com/licenses)
- three.js `KTX2Loader`: import from `three/addons/loaders/KTX2Loader.js`, call `setTranscoderPath(...)` (basis WASM in `examples/jsm/libs/basis/`, can be a CDN), then `detectSupport(renderer)` before loading. It supports Basis Universal textures transcoded to GPU formats, relies on WebAssembly — [three.js KTX2Loader docs](https://threejs.org/docs/pages/KTX2Loader.html)
- A community post describes extracting .gltf files from NASA Eyes via network inspection. This is not NASA guidance, so don't rely on it — [Celestia forum](https://celestiaproject.space/forum/viewtopic.php?p=159661)

### Inferences
- **Environment lighting:** `const pmrem = new PMREMGenerator(renderer); scene.environment = pmrem.fromScene(new RoomEnvironment(), 0.04).texture;` (`three/addons/environments/RoomEnvironment.js`) gives instant studio reflections, but it reads as "indoor". For space, better options: (a) build a **custom env scene** (black sphere + one big warm emissive quad for the sun direction + a faint blue rim panel + the actual baked sky cube) and PMREM it once, so reflections match the scene's light. (b) a CC0 Poly Haven HDRI (e.g., a dark studio or night HDR at 1k-2k, `.hdr` via `RGBELoader`), using `scene.environmentIntensity`-like control via `envMapIntensity` per material (r160 has per-material `envMapIntensity`). Cost: one-time PMREM (≈ tens of ms), negligible per frame.
- **Lighting rig ("cinematic product shot in space"):** a key directional sun (warm, high intensity, shadow-casting with a tight 1024-2048 shadow map around the ship only), a cool rim/back light from behind-camera-opposite (or a fresnel rim term in `onBeforeCompile`), and a very low fill from the planet ("planetshine": bounce color = planet albedo average). Remove generic ambient light (it flattens everything).
- **Material upgrades from primitives:**
  - Use `MeshPhysicalMaterial` for hero parts: `clearcoat` on painted panels, `iridescence` subtly on visor/cockpit glass, `sheen` not needed. `anisotropy` (r159+?) for brushed metal: verify availability in r160.
  - Generate **roughness/metalness/normal canvases** alongside albedo: panel seams as dark lines in albedo + grooves in normal (Sobel of a height canvas) + higher roughness in seams. Add a grime/edge-wear mask from noise × curvature approximation (use primitive UV edges). Small UV-scale details (rivets, decals: hazard stripes, registry numbers, tiny text) read as "premium".
  - **Decals:** `DecalGeometry` (three addons) for logos/markings on curved hulls, or bake them into the canvas textures.
  - **Emissive details:** window strips, nav lights (red port/green starboard, slow 2-3 s blink, calm), engine nozzles with HDR emissive (intensity 5-20) so bloom picks them up. Add engine exhaust as additive cones with a scrolling noise shader + a small point light flickering ±3% for warmth.
  - **Shading tricks:** fresnel rim in `onBeforeCompile` (`emissive += rimColor * pow(1.0 - dot(N,V), 3.0) * rimStrength`). Optional SSAO/GTAO is not needed in space. Instead bake AO into canvases (darken recesses).
  - **Geometry:** bevel edges (`RoundedBoxGeometry` from addons, or `ExtrudeGeometry` with `bevelEnabled`). Specular highlights on bevels are the #1 cue that separates "primitives" from "model". Add greebles via `InstancedMesh` (hundreds of small boxes/cylinders on the hull) at near-zero draw-call cost.
- **glTF route:** pick a CC0 (Poly Haven, Kenney, Quaternius) or CC BY Sketchfab spaceship, run `gltf-transform optimize` (Draco/Meshopt + KTX2) offline, host next to the HTML, and load with `GLTFLoader` + `DRACOLoader.setDecoderPath('https://www.gstatic.com/draco/versioned/decoders/1.5.6/')` + `KTX2Loader` (transcoder path `https://cdn.jsdelivr.net/npm/three@0.160.0/examples/jsm/libs/basis/`). That's offline tooling, but still "no build step" for the app itself. Keep the hero model ≤ 5-10 MB and ≤ 100k triangles for laptop/mobile.
- **Cost:** IBL + PBR on a ~50-100k-triangle ship is cheap on all targets. The ship's shadow map is the main extra (1 extra depth pass). MeshPhysicalMaterial clearcoat/iridescence add ALU but cover few pixels.
